# Write a useful task brief

[Home](../README.md) · [Learning path](../LEARNING-PATH.md)

## The idea

State the task, audience, available information, constraints, and desired output. Add only details that affect the result. A role can focus style or perspective, but calling a model an expert does not give it expertise.

## Try this prompt

```text
Rewrite the note below for a customer. Keep the delivery date and price unchanged. Use a calm tone and fewer than 80 words. If either fact is missing, say so. Note: Your order costs ₹900 and arrives Friday.
```

This is a practice prompt, not a recorded model response. Replace bracketed placeholders before using it.

## Practice and check

Remove one instruction at a time and observe what changes. Check the price and date literally.

Save the input, prompt version, model, output, and your checks. Explain one failure in your own words before revising the prompt.

## Common mistake

Too many overlapping rules make a prompt harder to follow. Resolve contradictory requirements.

## Before moving on

Can you explain when this technique helps, show one case where it fails, and describe how you checked the result? Use the [evaluation worksheet](../templates/evaluation.md) to record evidence.

## From vague request to testable brief

“Write a good email” leaves the purpose, reader, facts, and next action unclear. A better brief is: “Write to a customer whose shipment is delayed. Use only these facts: dispatch is pending; the next update is Friday. Ask whether they prefer email or phone updates. Keep it under 100 words.” Check each preserved fact and the requested action. Do not add a new delivery promise.

Put essential requirements ahead of decorative style. If two requirements conflict, resolve them explicitly.
