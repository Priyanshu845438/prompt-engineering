# Break a difficult task into checkable parts

[Home](../README.md) · [Learning path](../LEARNING-PATH.md)

## The idea

Separate requirements, candidate solutions, checks, and final output. Ask for a concise explanation or verifiable intermediate artifacts rather than private internal reasoning. Extra steps help only when they improve the task.

## Try this prompt

```text
Plan a two-hour HTML workshop for beginners. First list three measurable learning goals. Then propose activities and a time budget totaling 120 minutes. Finish with a short exercise that checks those goals.
```

This is a practice prompt, not a recorded model response. Replace bracketed placeholders before using it.

## Practice and check

Sum the minutes yourself and check whether the exercise tests every goal. Compare against a single-sentence request.

Save the input, prompt version, model, output, and your checks. Explain one failure in your own words before revising the prompt.

## Common mistake

A long explanation can hide an incorrect answer. Use a calculator or executable check for arithmetic.

## Before moving on

Can you explain when this technique helps, show one case where it fails, and describe how you checked the result? Use the [evaluation worksheet](../templates/evaluation.md) to record evidence.

## Planning without unnecessary narration

Ask for artifacts you can inspect: assumptions, equations, requirements, candidate designs, or tests. A short explanation is often more useful than pages of intermediate discussion. For a multi-step workflow, validate early results before passing them onward.

Use least-to-most when later subproblems depend on earlier answers. Use branching search only when exploring alternatives is necessary and you have an evaluator that can reject bad states. These are different approaches, not interchangeable phrases.
